FINDING-S015-001

SEVERITY=HIGH
CATEGORY=SCHEDULING_SAFETY

REPORTED=

ACTIVE_CADENCE=3600000ms
DEGRADED_CADENCE=1800000ms

This means a DEGRADED source is scheduled twice as frequently as a healthy ACTIVE source.

That contradicts the intended conservative degradation policy.

A degraded source must not be hammered more aggressively by normal discovery scheduling.

Required correction:

Either:

A)
DEGRADED discovery cadence must be slower than ACTIVE

or:

B)
the faster cadence must be strictly limited to a distinct, explicitly authorized
diagnostic/recovery task type and MUST NOT dispatch normal DISCOVERY_EXECUTION.

For V1, preferred correction:

ACTIVE discovery cadence = normal
LOW_PRIORITY discovery cadence = slower
DEGRADED discovery cadence = slower/restricted

Do not use DEGRADED state to increase ordinary collection load.

FINDING-S015-002

SEVERITY=HIGH
CATEGORY=DETERMINISTIC_IDENTITY

REPORTED=

slotId=
slot:${sourceId}:${slotFloorMs}

taskId=
task:sched:${sourceId}:${slotFloorMs}

These identities omit:

taskType
schedulingPolicyVersion

This creates future collision/aliasing risk.

Example:

same source
same time slot
DISCOVERY_EXECUTION

vs

SOURCE_HEALTH_EVALUATION

could map to the same logical task identity.

Likewise a scheduling-policy revision could reuse an old slot/task identity while semantics changed.

Required identity model must include stable discriminators equivalent to:

slot:
sourceId:
taskType:
scheduledFor:
schedulingPolicyVersion

and:

task:
sourceId:
taskType:
scheduledFor:
schedulingPolicyVersion

Exact string syntax may follow repository conventions.
