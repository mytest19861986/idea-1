Discovery Worker Runtime, Task Execution & Failure Isolation

OBJECTIVE=

Create a source-agnostic worker runtime contract that can execute Discovery Core jobs
reliably while providing:

deterministic task identity

bounded retries

retry/final failure classification

failure isolation

execution attempts

explicit task lifecycle

observability integration

idempotent replay behavior

without introducing a production queue, scheduler or database dependency yet.

CRITICAL DISTINCTION

WORKER RUNTIME
!=
SCHEDULER

WORKER RUNTIME
!=
QUEUE BROKER

WORKER RUNTIME
!=
SOURCE GOVERNANCE

The worker executes an explicitly supplied task.

It does not decide when a source should run.

WORK-I001 — EXPLICIT TASK CONTRACT

Create a versioned WorkerTask contract.

Conceptual fields:

taskId
taskType
sourceId

payloadReference / bounded payload

attempt
maxAttempts

createdAt
notBefore

executionId

taskVersion
retryPolicyVersion

No hidden timestamp.

WORK-I002 — DETERMINISTIC TASK IDENTITY

Task identity must be explicit and stable.

Do not regenerate taskId from wall-clock time during execution.

Same logical task replay
→ same taskId.

WORK-I003 — TASK TYPES

V1 should support only explicitly registered task types.

Examples:

DISCOVERY_EXECUTION
SOURCE_HEALTH_EVALUATION
SOURCE_GOVERNANCE_EVALUATION

Do NOT add arbitrary function execution.

Unknown taskType
→ FINAL_FAILURE / REJECTED

WORK-I004 — HANDLER REGISTRY

Worker runtime must dispatch through an explicit handler registry.

Conceptually:

taskType
→ registered handler

No eval()
No dynamic code execution
No arbitrary module path execution.

WORK-I005 — DOMAIN MODULE REUSE

Handlers must call existing approved boundaries.

Example:

DISCOVERY_EXECUTION
→ existing E2E/discovery orchestrator

Do not reimplement intake, storage, dedup, health or governance logic inside Worker.

WORK-I006 — TASK STATE MODEL

Minimum conceptual states:

PENDING
RUNNING
SUCCEEDED
RETRYABLE_FAILURE
FINAL_FAILURE
EXHAUSTED

If useful:

CANCELLED

may be reserved but should not be implemented without a real cancellation contract.

WORK-I007 — ATTEMPT HISTORY

Every execution attempt must create an immutable attempt result.

Conceptual:

taskId
attemptNumber
executionId
startedAt
finishedAt
outcome
failureKind
retryEligible
nextEligibleAt

Attempt history is append-only.

WORK-I008 — FAILURE TAXONOMY

Reuse existing failure semantics where available.

At minimum distinguish:

RETRYABLE_TECHNICAL_FAILURE
RATE_LIMITED
ACCESS_CONFIGURATION_FAILURE
POLICY_ACCESS_FAILURE
VALIDATION_FAILURE
FINAL_DOMAIN_FAILURE
UNKNOWN_FAILURE

Do not make all thrown exceptions retryable.

WORK-I009 — RETRY ELIGIBILITY

Retry policy must be deterministic and versioned.

Examples:

network/transient 5xx
→ RETRYABLE

rate limit
→ RETRYABLE with retry-after/backoff

401/missing credential
→ NOT automatically retried indefinitely

policy restriction
→ FINAL / MANUAL_REQUIRED

validation failure
→ FINAL

domain conflict
→ follow domain semantics, not blind retry.

WORK-I010 — MAX ATTEMPTS

Every task must have a bounded maxAttempts.

Infinite retry is forbidden.

Example:

attempt >= maxAttempts
→ EXHAUSTED

WORK-I011 — BACKOFF MODEL

Backoff policy must be explicit and versioned.

Recommended initial deterministic model:

retry-policy-v1

Allow:

fixed
exponential
provider retryAfter

but impose:

MAX_BACKOFF

No unbounded delay computation.

WORK-I012 — RETRY-AFTER

If upstream provides an explicit retryAfter:

worker may respect it within policy bounds.

Required:

effectiveDelay =
bounded(retryAfter, policy limits)

Do not trust arbitrarily huge or malformed values.

WORK-I013 — NO HIDDEN SLEEP IN DOMAIN

Domain modules must not sleep.

Retry timing belongs to worker/runtime scheduling boundary.

WORK-I014 — REPLAY SAFETY

Running the same task again must rely on existing idempotency guarantees.

Worker must not try to create a second idempotency system that conflicts with domain identity.

Examples:

candidate replay
→ REPLAYED

observation replay
→ not double counted

governance application replay
→ idempotent

WORK-I015 — FAILURE ISOLATION

One task failure must not crash or poison unrelated tasks.

Reference executor must demonstrate:

Task A fails
Task B succeeds

Worker process/runtime continues.

WORK-I016 — ERROR CONTAINMENT

Unhandled handler exception:

must be captured
normalized
classified

and represented as task failure.

Do not let arbitrary handler exception terminate the worker loop in reference runtime.

WORK-I017 — TELEMETRY INTEGRATION

Reuse PKG-OBS-013.

Required spans/metrics conceptually:

worker.task.execute
worker.task.attempt

worker_task_started
worker_task_succeeded
worker_task_retryable_failure
worker_task_final_failure
worker_task_exhausted

Include bounded labels only.

Do not put taskId/executionId in metric labels.

They may be trace/log correlation attributes.

WORK-I018 — TELEMETRY FAILURE ISOLATION

Telemetry failure must not change WorkerTask outcome.

WORK-I019 — CONFIDENTIALITY

Worker logs/errors/telemetry may not leak confidential payload fields.

Worker must not serialize entire task payload blindly into logs.

WORK-I020 — SECRET REDACTION

No:

Authorization header
API token
database credential
secret environment value

in attempt result, telemetry or errors.

WORK-I021 — TASK PAYLOAD BOUNDARY

Prefer bounded task references/normalized payloads.

Do not design the worker queue contract around arbitrary enormous raw HTML/document payloads.

Future queue infrastructure should not require transporting unlimited documents in message bodies.

WORK-I022 — NO SOURCE-SPECIFIC LOGIC

Forbidden:

if sourceId === "trustmrr"

Source-specific behavior belongs to collector/source adapters.

WORK-I023 — NO AUTOMATIC SOURCE ACTIVATION

Worker execution may not activate, reject or retire a source outside the existing governance contract.

WORK-I024 — LEASE / CLAIM MODEL

Define, but do not falsely claim distributed proof.

Reference runtime should define conceptual claim fields:

claimedBy
claimedAt
leaseExpiresAt

This prepares for future queue/multi-worker execution.

In this package:

DISTRIBUTED_LEASE_PROOF=NOT_REQUIRED

because no durable broker/database runtime exists yet.

WORK-I025 — LEASE EXPIRY SEMANTICS

Document expected future behavior:

RUNNING task

expired lease
→ eligible for reclaim

but only under durable coordination in a future package.

Do not simulate in-memory lease behavior and call it production-safe.

WORK-I026 — GRACEFUL EXECUTION BOUNDARY

Reference worker should complete one accepted task attempt cleanly.

Do not build process signal management or distributed shutdown complexity unless already needed.

Production graceful shutdown belongs to runtime hardening later.

WORK-I027 — NO QUEUE CLAIM

This package must not claim:

Kafka proven
Redis/BullMQ proven
SQS proven
RabbitMQ proven
Postgres queue proven

No production broker is part of the package.
