COMMANDER_DIRECTIVE

PACKAGE=PKG-OBS-013

TITLE=
Production Observability Contracts, Metrics & Structured Tracing

STATUS=AUTHORIZED

ORCHESTRATOR=ANTIGRAVITY
PRIMARY_IMPLEMENTER=GLM-5.3

GEMINI=OPTIONAL_FOR_SIGNAL_COVERAGE_REVIEW
QWEN=NO_ACTION
CLAUDE=NO_ACTION

OBJECTIVE=

Add source-agnostic observability boundaries across the Discovery Core
without changing domain behavior.

The system must expose enough structured telemetry to answer:

What happened?

Where did it fail?

Which source was affected?

Which execution caused it?

How long did each stage take?

Was the operation stored, replayed, rejected, blocked, or conflicted?

Did governance recommend or apply a transition?

Are collectors being rate-limited?

Are sources producing useful unique intelligence?

Observability must never become business logic.

OBS-I001 — OBSERVABILITY IS NON-AUTHORITATIVE

Metrics, traces and logs must not decide:

source lifecycle
candidate acceptance
entity match
claim classification
health score
governance transition

Telemetry observes approved domain decisions.

It does not create them.

OBS-I002 — DOMAIN OUTCOME FIRST

Telemetry must be derived from actual domain outcomes.

Forbidden:

telemetry reports candidate STORED
when persistence returned CONFLICT

telemetry reports governance APPLIED
when application returned STALE_DECISION

No optimistic/fabricated success telemetry.

OBS-I003 — CORRELATION MODEL

Support explicit correlation fields equivalent to:

executionId
sourceId
candidateId
observationId
decisionId
clusterId
collectorId

Include only identifiers that actually exist for that stage.

Do not fabricate unavailable IDs.

OBS-I004 — TRACE MODEL

Provide structured spans for major boundaries:

discovery.pipeline
discovery.intake
discovery.store
discovery.entity_resolution

source.health.evaluate
source.governance.evaluate
source.governance.apply

collector.execute

persistence.operation

Exact names may follow conventions.

Nested traces should preserve execution correlation.

OBS-I005 — METRIC MODEL

At minimum define source-agnostic metrics for:

collector attempts
collector successes
collector failures
rate-limit events
access/config failures

intake accepted
intake rejected

candidate stored
candidate replayed
candidate conflicted

attribution appended

resolution confirmed
resolution possible
resolution blocked
resolution distinct/unresolved

observations produced
observation replayed/conflicted

health evaluations
health confidence distribution

governance decisions
governance transitions applied
governance stale decisions
manual-review decisions

OBS-I006 — INTELLIGENCE CONTRIBUTION METRICS

Expose metrics such as:

unique candidates
duplicate candidates
new attributions
confirmed entity links

but do not independently recompute the SourceHealthEvaluator formula.

Observability may measure inputs/outcomes.

It must not become a second health evaluator.

OBS-I007 — LATENCY

Capture stage duration.

Use monotonic duration measurement where runtime implementation supports it.

Do not use wall-clock timestamps to calculate elapsed duration if a monotonic timer is available.

Domain deterministic timestamps remain separate from operational timing.

OBS-I008 — STRUCTURED LOGGING

Logs should be structured records.

Recommended levels:

DEBUG
INFO
WARN
ERROR

Each event should contain an event name/code rather than relying on prose parsing.

OBS-I009 — SECRET REDACTION

Never emit:

API tokens
Authorization headers
database URLs containing credentials
cookies
secret environment variables

into:

logs
traces
span attributes
metrics labels
error serialization

OBS-I010 — CONFIDENTIALITY

Confidential Candidate protection extends to observability.

Do not log or trace:

sanitized confidential domain
original contentReference
masked entity identifying metadata

Telemetry may carry:

candidateId
sourceId
confidential=true

where safe.

OBS-I011 — METRIC CARDINALITY

Do NOT use high-cardinality identifiers as metric labels.

Forbidden as normal metric labels:

executionId
candidateId
observationId
decisionId
canonicalUrl

They may appear in structured traces/log correlation.

Safe metric dimensions may include bounded values like:

sourceId
status
stage
failureKind
decisionType

SourceId cardinality must still be understood and documented.

OBS-I012 — ERROR TAXONOMY

Preserve existing distinctions:

TECHNICAL_FAILURE
RATE_LIMIT_PRESSURE
ACCESS_CONFIGURATION_FAILURE
POLICY_ACCESS_FAILURE

Do not collapse them into generic ERROR metrics only.

OBS-I013 — REPLAY VISIBILITY

Idempotent replay must be observable distinctly from new writes.

Example:

candidate STORED
candidate REPLAYED
candidate CONFLICT

must remain separate outcomes.

OBS-I014 — GOVERNANCE SAFETY VISIBILITY

Expose separately:

decision generated
automatic transition authorized
transition applied
manual review required
stale decision
blocked transition

Do not count a decision as an applied transition.

OBS-I015 — PROVIDER ABSTRACTION

Domain modules should not depend directly on OpenTelemetry SDK APIs.

Use an observability port/facade.

Conceptually:

TelemetryPort

startSpan(...)
recordMetric(...)
log(...)

Production OpenTelemetry adapter may sit behind the port.

OBS-I016 — NO-OP ADAPTER

A NoopTelemetry adapter must exist.

The Discovery Core must function correctly when observability is unavailable.

Telemetry outage must not stop core domain processing.

OBS-I017 — TELEMETRY FAILURE ISOLATION

Unless explicitly classified as a critical operational requirement:

metric export failure
trace export failure
logging sink failure

must not change domain outcome.

Telemetry errors should be isolated.

OBS-I018 — OTEL ADAPTER BOUNDARY

A real OpenTelemetry-compatible adapter is authorized.

However external collector/export infrastructure is not required in this package.

Allowed:

SDK integration
in-memory test exporter
console/local structured exporter for testing

Not required:

production Grafana
production Tempo
production Prometheus
production OTLP endpoint

OBS-I019 — VERSIONING

Telemetry schema/event naming should have an explicit version.

Recommended:

discovery-observability-v1

This allows dashboards and alerting contracts to evolve safely.

OBS-I020 — NO HIDDEN BUSINESS MUTATION

Observability instrumentation must not mutate:

SourceRecord
RawDocument
CandidateDiscoveryRecord
Attribution
ResolutionDecision
SourceHealthSnapshot
GovernanceDecision

IMPLEMENTATION TARGET

Recommended modules:

src/observability/telemetry.mjs
src/observability/noop-telemetry.mjs
src/observability/otel-adapter.mjs

plus minimal instrumentation at approved orchestration boundaries.

Do not scatter arbitrary instrumentation through every low-level function if
an orchestration boundary can produce the same evidence cleanly.

INSTRUMENTATION PRIORITY

E2E Orchestrator

Discovery Pipeline

Collector execution boundary

Persistence adapter boundary

Health evaluator

Governance evaluator/applier

Prefer boundary instrumentation over invasive domain rewrites.

telemetry adapter disabled
